# План разработки

Рабочий журнал задач проекта «виртуальный стол для D&D». Файл можно и нужно
править: отмечайте сделанное, добавляйте своё, выбрасывайте ненужное.

- `[ ]` — не начато, `[~]` — в работе, `[x]` — готово.
- Приоритеты: **P0** — без этого рискованно играть по сети; **P1** — заметно
  улучшает стол; **P2** — полировка и вкусности.
- Оценка: **S** — один вечер, **M** — два-три вечера, **L** — больше недели
  вечеров.
- Правила ведения — в `AGENTS.md`. Пункт считается готовым только вместе с
  тестами (`ctest`), ручной проверкой «хост + клиент» со скриншотами окна,
  обновлением `AGENTS.md` и коммитом на русском.

## Состояние на 22.11.2026

Готова играбельная основа:

- Хост/DM и TCP-клиенты, меню Host/Join/Map, пароль (challenge-response),
  лобби с составом, `/kick`, лимиты пиров и команд, `TCP_NODELAY`. После
  правки мира пиру уходит только его дельта вида — токены, вошедшие в туман
  или ушедшие из него, и изменившиеся клетки тумана; полный `ViewUpdated`
  остаётся для входа и смены сцены.
- Туман войны на каждого игрока: обзор только от его персонажей, чужие
  токены скрыты, исследованные клетки помнятся; у DM — `/reveal`. До выбора
  персонажа игрок видит общий обзор партии.
- Бой: автобросок инициативы с бонусом из листа, раунды, ходы, лимит движения
  по скорости (диагонали по правилу 5–10–5), сброс запаса в начале хода.
- Токены: типы, владельцы, claim/release одним персонажем, `/owner`, лист
  персонажа (КД, скорость, бонусы, урон, заметки, временные HP, кость хитов,
  модификатор Телосложения), состояния с длительностью, цвета,
  переименование, max HP, опыт и уровень, портреты.
- Уровень по правилам 2024: прирост максимума и текущих HP по среднему кости
  хитов и модификатору Телосложения, бонус мастерства по рубежам (5/9/13/17
  поднимает бонусы атаки и спасброска в листе), напоминания о повышении
  характеристик (4/8/12/16) и эпическом даре (19).
- Кубы: `/roll`, `adv`/`dis`, атака (Shift — преимущество, Ctrl — помеха),
  спасбросок, инициатива, урон; подписи с именем токена.
- Атака автоматизирована: `A` по цели под курсором сравнивает d20 + бонус с
  КД, крит удваивает кости урона, промах и 1 не наносят урона; сервер сам
  применяет урон из листа цели (временные HP, «без сознания», концентрация).
- Правила: урон и лечение, временные HP, спасброски от смерти, концентрация,
  отдых по костям хитов (короткий тратит, длинный возвращает), шаблоны
  областей (круг/конус/линия) со спасбросками.
- Метры (1 клетка = 1,5 м), дальность движения с учётом тумана, линейка по
  `Alt`+ЛКМ, пинг `Alt`+ПКМ, проверка пути вне боя.
- Бестиарий из 9 шаблонов, спавн одного монстра и группы 3–5 (`Shift`+цифра)
  в свободные клетки вокруг курсора.
- Кампания из сцен: библиотека `*.dndcamp` рядом с `.exe` с выбором в меню,
  панель по `Tab`, `/scene`, копирование/удаление сцен, заметки и
  переименование, автосейв в фоновом потоке, смена сцены с полной
  пересинхронизацией через `ViewUpdated`.
- Редактор карт: стены и рельеф (дерево, вода, пропасть, лава), размер,
  стартовые токены, `scene.dndscene`; имя карты и «N из M» в панели,
  переименование `R`, удаление двойным `Del`, рисование и стирание с зажатой
  кнопкой без дыр между клетками.
- Стол: прокрутка лога, `session.log`, справка `F1`, журнал `F3` с поиском и
  прошлыми сессиями, масштаб интерфейса, мышь в списках, подложка карты,
  круглые портреты, `Ctrl+Z` для DM, подтверждение удаления двойным `Del`.
- Разбор чат-команд в ядре (`ParseChatCommand`) с тестами; в `net_tests`
  есть сценарий двух клиентов за столом.
- Логика стола вне SDL: камера и зум, меню, навигация по сценам и файлам,
  отложенный автосейв и фоновая запись кампании, прокрутка лога, подтверждение
  удаления и строка чата живут в `src/core` и покрыты `core_tests`; `App`
  осталась клеем между SDL и командами.

Версии форматов: `kSaveVersion = 30`, `kProtocolVersion = 41`,
`kCampaignVersion = 16`. Тесты — `core_tests` и `net_tests`, оба зелёные;
P0 «Смерть, отдых и концентрация», P0–P1 «Ход, действия и недееспособность»
и P1 «Состояния, урон и атаки», «Встреча и вступление в бой»,
P1–P2 «Отдых, время и движение» закрыты,
действия в чужой ход и экономика хода проверяются `core_tests`.
Свои файлы собираются с `-Wall -Wextra -Wpedantic` без предупреждений;
`clang-tidy` по флагу `-t` замечаний не находит. Интерфейс проверен на живом
окне (хост + клиент): отдельный туман, `M`, отказ «Клетка не разведана»,
`/xp`, `Ctrl+Z`, `/reveal`, `/unreveal`, журнал `F3` с поиском, `КХ` в
карточке токена и фоновый автосейв (ход гоблина, запись через 8 секунд и
загрузка того же мира после перезапуска); панель `K` с палитрой 2024 и
своим состоянием, лист с типом урона и защитами, `/damage 4 дробящий` с
уязвимостью и атака «с помехой» по невидимой цели, редактор карт с именем
и счётчиком карты, переименованием, удалением двойным `Del` и рисованием
с зажатой кнопкой — со скриншотами.

## Аудит: что мешает и чего не хватает

Проверено чтением кода и на живом окне (хост + клиент, 21.11.2026).
Расхождения именно с правилами 2024 собраны отдельно — «Аудит правил
22.11.2026» ниже.
Закрыто с прошлого аудита: открытый пароль, невнятный отказ при чужой
версии, отсутствие лимитов, `TCP_NODELAY`, партийный туман, состояния без
длительности/отдыха/опыта/концентрации, подложка и портреты, путь вне боя,
сброс тумана при `Reset` (пункт 4), регистр имён (пункт 9), открытый трафик
(пункт 2), повышение уровня (пункт 5), атака с уроном (пункт 6), точечное
закрытие открытых областей (пункт 7), инкрементальная синхронизация вида
(пункт 8), чтение и поиск журнала (пункт 10), отдых по костям хитов
(пункт 11), фоновая запись автосейва (пункт 12).

1. **Сеть только под Windows**: `#error` в `src/net/tcp_socket.cpp`; сборка
   и тесты на Linux/macOS не пойдут.
2. **Трафик открыт** — готово: после рукопожатия все кадры шифруются
   (X25519 + ChaCha20 + HMAC-SHA256, ключи через HKDF-SHA256). Открытыми
   остаются только `Challenge`, `Hello` и отказ до проверки пароля.
3. **Логика `App` без тестов** — готово: камера (`core/camera`), переход
   по вкладкам и полям меню с разбором адреса (`core/menu_model`),
   навигация по сценам и файлам (`core/navigation`), отложенный автосейв
   (`core/autosave`), прокрутка лога (`core/log_scroll`), подтверждение
   удаления (`core/delete_confirm`), строка чата и UTF-8-ввод
   (`core/chat_input`, `core/utf8`) вынесены в ядро и покрыты
   `core_tests`. В `App` остались SDL, отрисовка и связывание команд;
   панели по-прежнему проверяются на живом окне.
4. **Туман обнуляется при `Reset`** — готово: туман хранится в сцене
   (`GameSnapshot::fog`, только исследованные клетки), сервер восстанавливает
   его в `GameServer::Reset`, поэтому `Ctrl+Z`, `F9` и смена сцены больше не
   заставляют игроков исследовать карту заново. Карта другой формы начинает
   с чистого тумана, клиенту уходит только его срез.
5. **Повышение уровня ничего не даёт** — готово: уровень по-прежнему
   вычисляется по опыту, но повышение меняет лист по правилам 2024.
   За каждый новый уровень максимум HP растёт на среднее кости хитов
   (d6 4, d8 5, d10 6, d12 7) плюс модификатор Телосложения, но не меньше 1;
   текущие HP растут на столько же, если персонаж не лежит на нуле. На
   рубежах 5/9/13/17 бонус мастерства (+2…+6 по уровню) поднимает итоговые
   бонусы атаки и спасброска в листе, на 4/8/12/16 лог напоминает о
   повышении характеристик, на 19 — об эпическом даре. Кость хитов и
   модификатор Телосложения — поля листа (`L`); КД от уровня в 2024 не
   зависит, поэтому остаётся ручным.
6. **Атака не автоматизирована** — готово: `A` бьёт токен под курсором
   выбранным токеном. Сервер бросает d20 + бонус атаки против КД цели,
   natural 20 — критическое попадание с удвоенными костями урона, natural 1 —
   промах. При попадании урон из листа применяется сразу: временные HP,
   «без сознания» и проверка концентрации те же, что у `/damage`. Shift+A —
   преимущество, Ctrl+A — помеха. Цель должна быть видна атакующему.
   Чистая проверка броска и крит-урона — `core/attack`, тест — `TestAttack`;
   версия протокола — 31.
7. **`/reveal off` стирает все открытые клетки**, точечно закрыть участок
   нельзя — готово: `/unreveal` закрывает круг 4 клетки под курсором, не
   трогая остальные открытия, `/reveal off` по-прежнему снимает все.
   `GameState` хранит `revealed_` отсортированным по (y, x): `IsRevealed` —
   двоичный поиск, `RevealArea`/`HideArea` сливают и вычитают области за
   один проход вместо линейного поиска на каждую клетку. Версия протокола —
   32, тесты — `TestRevealedAreas`, `TestSeparateVisibility`.
8. **Полный снапшот каждому пиру на каждое изменение мира** (`ViewUpdated`) —
   готово: после правки мира хост считает дельту вида на игрока и шлёт только
   её. Токены, вошедшие в туман, уходят `TokenAdded`, ушедшие из него —
   `TokenRemoved`, а изменившиеся клетки тумана (видимость и разведанность)
   едут в `FogChanged`. Слепок «уже отправлено» держит `GameServer`
   (`TakeViewDelta` обновляет его сам, `MarkViewSent` начинает заново после
   полного вида), поэтому полный снапшот ходит лишь при входе и смене мира.
   Трафик правки больше не зависит от размера карты. Версия протокола — 35,
   тесты — `TestIncrementalView`, `TestFogChangedRoundtrip`.
9. **Кик обходится сменой регистра** — готово: имена игроков сравниваются
   без учёта регистра (`PlayerNameKey`/`SamePlayerName` в
   `src/core/player_name`), поэтому кик по `player` закрывает вход и как
   `Player`, дубликаты имён ловятся в любом регистре, а персонаж с владельцем
   `player` отдаётся игроку `Player`. Тем же ключом живёт туман игроков.
10. **Лог в памяти — 200 строк**, интерфейс не читал `session.log` — готово:
    `F3` открывает модальный журнал (`core/log_history`,
    `DrawLogHistoryPanel`) и читает файл с диска: последние
    `kMaxHistoryLines` (2000) строк, хвост не больше 512 КиБ, чтобы старый
    журнал не грузился целиком. Заголовки `=== сессия ... ===` разделяют
    прошлые сессии, поиск по автору и тексту идёт без учёта регистра тем же
    ключом, что и имена (`PlayerNameKey`); Enter не нужен — фильтр
    пересчитывается на каждый символ. `↑`/`↓`, `PgUp`/`PgDn`, колесо и
    `End` листают найденное. Тест — `TestSessionLogHistory`.
11. **Отдых и уровни не связаны с правилами** — готово: отдых идёт по
    костям хитов (2024). Запас костей равен уровню (`HitDiceMaximum`), тратится
    коротким отдыхом `/rest`: каждая кость лечит `HitDieHeal(d{h}, Телосложение)`
    (не меньше 0), пока не восстановлен максимум HP или не кончились кости.
    Длинный отдых `/longrest` возвращает HP, все кости и снимает состояния.
    Потраченные кости хранит `Token::hit_dice_spent`, их видно в карточке
    токена (`КХ: осталось/всего`), отдых пишет подробную строку в лог.
    Версии сохранения и протокола — 26 и 36, тесты — `TestShortRestHitDice`,
    `TestDamageHealRest`, `TestLevels`.
12. **Автосейв пишет всю кампанию синхронно** в кадре — готово: кампанию
    пишет `CampaignSaver` (`core/campaign_save`) в отдельном потоке. Копия
    мира снимается в момент просьбы, поэтому кадр не ждёт ни кодирование, ни
    диск; новая просьба заменяет ещё не начатую, и на диск уходит самый
    свежий мир. Явные сохранения (`F5`, смена сцены, старт хоста) по-прежнему
    доходят до диска вызовом `Flush`, а итог автосейва `App` опрашивает в
    кадре. Если мир изменился, пока шла запись, `AutosaveTimer::
    ChangedDuringSave` планирует ещё один проход через полную паузу, так что
    правки не теряются. Тесты — `TestCampaignSaver`, `TestAutosave`.

## Аудит правил 22.11.2026

Сверка кода с `docs/rules/cheatsheet-ru.md` и SRD 5.2.1, плюс чтение
`core_tests`. Тесты были зелёные, но часть проверок закрепляла неверное
поведение, поэтому «зелёный ctest» здесь не приёмка. В этом проходе код не
менялся, ниже задачи с приоритетом, файлами и приёмкой; P0 закрыт
отдельным коммитом (см. пометки «готово»).

Соответствует правилам и переделки не требует: автобросок инициативы с
бонусом из листа, натуральные 1/20 на атаке, крит удваивает кости без
модификатора, прирост HP по среднему кости и бонус мастерства на
5/9/13/17, временные HP принимают урон первыми, 5–10–5 и трудная
местность, туман от своих персонажей, спасбросок состояния в конце хода,
урон и лечение через общий `DamageAndLog`.

Незакрытые этапы вне правил: 2.5 (панель, имена, удаление и рисование в
редакторе), 2.6 (свойства клеток), 7.5–7.7 (несовпадение версий, риски и
проверка обновлений), 8 (кампания и оверлей партии), пункт 1 старого аудита
(TCP только под Windows).

Приёмка любого пункта — как в правилах проекта: `ctest`, новый тест на
исправленное поведение, живое окно со скриншотом изменённого вида,
обновление `AGENTS.md` и коммит на русском.

### P0. Смерть, отдых и концентрация (M) — готово

- [x] **Спасброски от смерти по SRD** — готово. `DeathSave` даёт два провала
      за натуральную 1 и два провала за удар по лежачему от критического
      попадания (обычный удар — один). `DamageToken` принимает признак
      крита, `HandleAttack` передаёт его через `DamageAndLog`. Остаток урона
      не меньше максимума HP убивает сразу, даже если персонаж ещё стоял
      (Instant Death из SRD 5.2.1). Тест — `TestDeathSaves`.
- [x] **Стабильность не снимает «без сознания»** — готово: три успеха
      оставляют `kUnconscious` на нуле HP, снимает его только лечение или
      возврат HP; стабильный больше не бросает спасброски. Тест —
      `TestDeathSaves`.
- [x] **Долгий отдых не воскрешает и не снимает всё подряд** — готово:
      длинный отдых возвращает HP, все кости хитов, обнуляет временные HP и
      снимает ровно один уровень истощения, остальные состояния остаются.
      Отдых (и короткий, и длинный) даёт эффект только персонажу хотя бы с
      1 HP: мёртвый и стабильный на нуле не встаёт, кости не тратит. Лог
      перечисляет восстановление без фразы «состояния восстановлены» и
      напоминает про лежачих. Тест — `TestDamageHealRest`.
- [x] **Короткий отдых: минимум 1 HP за кость** — готово: `HitDieHeal`
      возвращает `max(1, …)`. Тесты — `TestShortRestHitDice`, `TestLevels`.
- [x] **Концентрация** — готово: КС считается `ConcentrationDc` (10 или
      половина урона, не выше 30), смерть, 0 HP и недееспособность
      (`IsIncapacitatingCondition`: без сознания, выведен из строя,
      парализован, оглушён, окаменел, мёртв) снимают концентрацию без
      спасброска, в том числе при правке состояний через панель `K`. Тест —
      `TestConcentration`.
- [x] **Упрощение спасброска** — готово как явная пометка: в листе поле
      называется «Спасбросок (все)», один бонус идёт на состояния,
      концентрацию и урон по области; отдельные спасброски по способностям
      остаются в P1 «Состояния, урон и атаки».

### P0–P1. Ход, действия и недееспособность (M) — готово

- [x] **Сервер проверяет, чей ход** — готово. `HandleMove`, `HandleAttack` и
      `HandleUseTurnAction` смотрят на `ActiveTokenId`: игрок двигается и
      действует только в свой ход, вне боя ограничений нет, DM свободен.
      `TurnRejectReason` запрещает ход и атаку при 0 HP и состояниях
      недееспособности (без сознания, выведен из строя, парализован,
      оглушён, окаменел, мёртв). Вне своего хода атака требует
      `AttackToken::reaction`, тратит реакцию и бьёт только соседнюю цель;
      уклонение цели даёт помеху. Действие, бонусное действие и реакция
      живут в `Token` и сбрасываются в начале своего хода.
- [x] **Экономика хода (2024)** — готово. Панель `X` (`UseTurnAction`)
      предлагает рывок, отход, уклонение, помощь, скрыться, поиск, изучение
      и использовать предмет. `action_used` не даёт второй атаки за ход;
      рывок добавляет скорость движения (`movement_bonus`), отход и
      уклонение действуют до начала следующего хода, остальные приёмы

### 2.5 Редактор карт: выбор, имена и рисование (P1, S–M) — готово

Карта в редакторе — это сцена активной кампании (`Campaign::scenes`).
Отдельный список `*.dndscene` не заводим: кампания уже выбирается в меню
хоста и хранит сцены, второй источник правды разошёлся бы с ней. Выбор уже
был: `Tab` открывает список сцен, `↑`/`↓`, `1`–`9` и двойной клик открывают
карту, `N` делает копию; ниже — имя карты в панели, переименование, удаление
и рисование с зажатой кнопкой.

- [x] **Панель и выбор карты (S).** В заголовке панели редактора — имя
      открытой карты и «N из M» списка; после открытия/создания/переименования
      `editor_status_` называет карту. `Tab`-панель показывает активную (`*`) и
      выбранную (`>`), подсказка дополняется `R` и `Del`.
      Переключение карты сохраняет правки текущей в `campaign_.scenes[...]`
      и пишет кампанию на диск (`SaveCampaign()`), чтобы `Esc` из редактора не
      терял карту; `F5` по-прежнему пишет ещё и `scene.dndscene`.
- [x] **Переименование (S).** В панели редактора `R` — правка имени выбранной
      карты: поле `editor_scene_edit_`, буфер, игнор первого `TEXT_INPUT`
      (это сама клавиша `R`), `Backspace` через `EraseLastCodePoint`, `Enter`
      — применить, `Esc` — отмена. Проверки те же, что у сцен DM:
      `TrimText`, `kMaxSceneNameLength`, `IsSceneNameAvailable` /
      `RenameScene`, ошибки «Имя не может быть пустым» / «Имя уже занято» в
      `editor_scenes_status_`. `App::RenameSceneAt` не переиспользуем: он
      проверяет режим хоста и пишет в `view_`, которого в редакторе нет —
      берём `dnd::RenameScene` напрямую. `campaign_.active` и `editor_scene_`
      едут за переименованием, затем `SaveCampaign()`.
- [x] **Удаление (S).** `Del` в панели удаляет выбранную карту после второго
      `Del` в течение 3 с (`core/delete_confirm`, свой `delete_editor_scene_`);
      последняя карта не удаляется. Индекс после удаления — `IndexAfterDelete`;
      если удалили открытую карту, редактор берёт соседнюю (`scene_`,
      `encounter` и выделение сбрасываются, `CenterCamera()`), иначе текущая
      карта остаётся, а `editor_scene_` сдвигается. Затем `SaveCampaign()`.
      Структуру кампании `Ctrl+Z` не отменяет — как и у сцен DM. Правило
      «последнюю нельзя» вынести в `CanDeleteScene(campaign)` рядом с
      `IsSceneNameAvailable` и использовать в панели DM и в редакторе;
      `App::DeleteActiveScene` не переиспользуем — он делает `ResetWorld` и
      объявление всему столу. Строка статуса панели живёт 3 с
      (`core/status_message`): предупреждение про повторный `Del` и отказ
      «нельзя удалить последнюю карту» сами уступают место подсказке.
- [x] **Рисование и стирание с зажатой кнопкой (S–M).** ЛКМ ведёт кисть и не
      рисует поверх токена; ПКМ возвращает полу, пока кнопка нажата, а токен
      под курсором удаляется только вторым ПКМ в течение 3 с
      (`delete_editor_token_`). Состояние
      `editor_paint_mode_` и `PaintDrag editor_stroke_`:
      `MOUSE_MOTION` применяет кисть только при переходе в другую клетку,
      клики по панели и клетки вне карты игнорируются; `MOUSE_BUTTON_UP` любой
      кнопки, потеря фокуса, смена карты и открытие панели заканчивают штрих.
      Между далёкими клетками — линия по Брезенхему (`core/editor_paint`),
      иначе быстрый взмах оставляет дыры. Туман и открытые области стирание не
      трогает.
- [x] **Токены в редакторе (S).** ЛКМ по токену выбирает его и таскает по
      клеткам, кисть поверх токена не рисует; проверка клетки (границы карты,
      непроходимый рельеф, занятость) — `core/editor_token`, тест
      `TestEditorTokenMove`. `R` переименовывает выбранный токен прямо в
      панели редактора, `V` переключает цвет палитры стола, `L` открывает
      редактируемый лист (`DrawSheetPanel`): правки уходят прямо в `scene_`,
      а `F5` и смена карты сохраняют их в кампанию. Проверка полей листа общая
      со столом (`ReadSheetValues`), ошибки показываются в панели редактора.
- [x] **Логика в ядре и тесты (S).** `src/core/editor_paint.{h,cpp}`:
      `PaintDrag::Begin(Cell)`, `PaintDrag::Move(Cell)` → `std::vector<Cell>`
      (пусто без `Begin` и если клетка та же; иначе линия от прошлой клетки
      до новой), `PaintDrag::End`; без SDL, выход за карту фильтрует `App`. `TestEditorPaint`
      в `core_tests`: повтор клетки, диагональ, далёкий скачок, конец штриха.
      `TestSceneDeleteRules` — `CanDeleteScene` для одной и нескольких сцен.
- [x] **Версии форматов не меняются**: новых полей в `Token`, `GameSnapshot`,
      `Command` и `Event` нет, это состояние редактора внутри `App`.
- [x] **Документация**: `AGENTS.md` (клавиши редактора: `R`, `Del` дважды,
      перетаскивание кистью), `README.md` (строка редактора в таблице клавиш),
      `strings.h` (`kEditorScenesHint`, `kEditorMouseHint`, новые тексты
      ошибок).
- [x] **Живая проверка (обязательно, скриншоты окна)**: `--editor` на окне —
      панель с именем карты; `Tab` → выбор другой карты, `Enter`, `Esc`;
      `R` с пустым, занятым и корректным именем; `Del` один и два раза, отказ
      на последней карте; зажатая ЛКМ по диагонали и через несколько клеток,
      ЛКМ по токену выбирает и перетаскивает его и ничего не рисует, зажатая
      ПКМ по стене, двойная ПКМ по токену, гаснущие сообщения панели;
      переименование `R` с пустым и корректным именем, лист `L` с правкой поля
      и повторным открытием, цвет `V` по палитре; после перезапуска карты на
      месте и с новыми именами; `F5`/`F9` и `Enter` в игру.
- [x] **Коммит** на русском: «Редактор карт: выбор, имена, удаление и рисование
      с зажатой кнопкой».

Порядок: панель и имя → рисование (ощутимее всего) → переименование →
удаление → документация → живая проверка. Всё, кроме рисования, — S; вместе
— M.

### 2.6 Свойства клеток карты (P1–P2, L) — план

Сейчас `GridMap::Terrain` отвечает только за проходимость и общий вид: стена,
дерево, вода, пропасть, лава. Правилам 2024 (5.5e) этого мало — нужны трудная
местность, укрытие, затемнение, глубина воды, течение, урон при касании и
дороги. Добавляем слой свойств поверх рельефа, а не заменяем `Terrain`: старые
сцены читаются с нулевыми свойствами, а знакомые клетки получают разумные
значения по умолчанию. Формулировки правил сверяются по
`docs/rules/cheatsheet-ru.md` и `docs/rules/SRD_CC_v5.2.1.pdf`.

- [ ] **Модель и формат (M).** `struct CellProps`:
      `flags` (дорога, можно лазать, скользко), `light` (ярко/тускло/темно),
      `obscurement` (нет/слабое/сильное), `water` (сухо/мелко/глубоко),
      `current_dir` (0–8), `current_strength` (0–3), `hazard` (индекс в
      палитре), `slippery_dc`, `cover_sides` — по 2 бита на сторону
      (0 — нет, 1 — половина, 2 — три четверти, 3 — полное).
      `GridMap` хранит `std::vector<CellProps>` параллельно рельефу и
      `std::vector<Hazard>` на карту: `DiceExpression`, тип урона, биты
      триггеров (вход, начало хода, конец хода, касание), КС спасброска,
      половина урона при успехе. Палитра не раздувает каждую клетку: клетка
      ссылается на профиль, одинаковые кисти переиспользуют его. Болото,
      грязь, снег и заросли — отдельные визуальные значения рельефа, но
      правило у них одно: трудная местность; глубина воды и укрытие остаются
      свойствами клетки.
- [ ] **Движение (M).** `MovementCost(cell, MovementProfile)` возвращает
      стоимость входа: трудная местность — 2, дорога — 1 и отменяет трудную
      местность, мелкая вода — 2, глубокая — плавание за 2, лазание — 2,
      диагональ 5–10–5 применяется после. `MovementProfile{скорость,
      плавание, лазание}` собирается из листа токена, `GridMap` о токенах не
      знает. По правилам 2024 трудная местность
      не складывается: болото с водой всё равно 2, а не 3–4. `ReachableCells`
      и `PathCostCells` считают по этой функции, `M` и лимит хода совпадают.
      У токена появляются `swim_speed` и `climb_speed` (0 — нет скорости) с
      полями в листе `L` и сериализацией; без скорости плавание/лазание
      остаётся возможным, но по правилам проверки.
- [ ] **Вода и течение (M).** Глубокая вода — плавание: 1 фут стоит 2,
      бурная вода требует проверки Силы (Атлетика) с КС из свойства; полностью
      погружённый получает сопротивление огню, дальнобойные атаки под водой —
      с помехой в обычной дистанции и автоматический промах за ней (2024).
      Течение: направление и сила, в начале хода и при входе — проверка
      Атлетики, при провале сдвиг на 1–3 клетки по течению с проверкой
      столкновений, без траты движения и без провокации атак; в лог идёт
      причина. Значения по умолчанию (сдвиг 3 клетки, КС 15) настраиваются,
      потому что DMG 2024 даёт их как пример, а не жёсткую формулу.
- [ ] **Укрытие (M).** Укрытие по стороне клетки, а не «на всю клетку»:
      `CoverBetween(map, attacker, target)` идёт по линии взгляда и берёт
      лучшее укрытие среди пересечённых граней. Половина — +2 к КД и
      спасброскам Ловкости, три четверти — +5, полное — цель нельзя выбрать
      напрямую (но область, накрывающая клетку, всё ещё действует). Учитывать
      в `AttackToken`, в уроне атаки и в спасбросках шаблона `Aoe`. Стены уже
      дают полное укрытие через `BlocksSight`; свойства нужны для низких стен,
      мешков, валунов и брустверов. Укрытие от существ (союзник между
      атакующим и целью) в первой версии не автоматизируем — решает DM.
- [ ] **Видимость: дым, туман, заросли (M).** Слабое затемнение — помеха на
      проверки Мудрости (Восприятие), сильное — фактически «ослеплён» для
      зрения: атаки с помехой, по нему — с преимуществом. Сильное затемнение
      (дым, плотный туман) не даёт смотреть сквозь клетку, но сама клетка
      видна как облако; слабое — видно сквозь. Туман войны по-прежнему хранит
      исследованные клетки, затемнение — отдельный слой поверх него. Токен в
      сильном затемнении скрывается от игроков, чья линия взгляда упирается в
      дым, но остаётся виден тем, кто внутри и DM. Дерево сохраняет текущее
      правило «видно ещё две клетки» и дополнительно даёт слабое затемнение.
- [ ] **Свет и тёмное зрение (P2, M).** Уровень освещённости на клетку:
      яркий, тусклый, тёмный. Тусклый — слабое затемнение, тёмный — сильное;
      у токена поле «тёмное зрение, м» (0 — нет), в тумане войны тёмное зрение
      превращает тьму в тусклый свет, а тусклый — в яркий в пределах радиуса.
      Без тёмного зрения игрок видит только клетки, куда достаёт свет; DM
      видит всё. Это отдельный шаг после дыма: он меняет расчёт тумана и
      требует поля в листе.
- [ ] **Урон при касании (M).** Триггеры: вход (первый раз за ход), начало
      хода, конец хода, касание. `GameServer` бросает урон из профиля, при
      спасброске с КС — половина, дальше тот же `DamageAndLog`: временные HP,
      «без сознания», концентрация. Повторный вход в ту же лаву за ход урона
      не повторяет: у токена набор сработавших профилей, очищается в начале
      хода и в конце боя. Лава по умолчанию — 10d10 огня (DMG 2024), кислота,
      шипы и огонь — готовые профили; сопротивления и иммунитеты пока не
      моделируем, тип урона только пишется в лог.
- [ ] **Дороги (S).** Дорога отменяет трудную местность и даёт обычную
      стоимость; в бою бонуса к скорости нет — в 2024 дорога влияет на
      путешествие, а не на ход. Вне боя хорошая дорога поднимает максимальный
      темп партии на шаг (медленный → обычный → быстрый), как Good Roads в
      SRD 5.2.1. Рисуется линией/цветом, поверх неё видны клетки болота и
      камней.
- [ ] **Лёд, лазание и прочее (P2, S–M).** Скользкая клетка: при движении
      больше половины скорости — проверка Ловкости (Акробатика) с КС или
      «сбит с ног». Лазаемая стена/уступ: вход стоит 2, со скоростью лазания —
      1; лестница — обычная стоимость. Это закрывает «забытое» из правил
      окружения: лёд, крутые склоны, лестницы, узкие уступы. Высоту и падение
      (1d6 за 10 футов), сильный ветер, жару/холод и удушье в дыму оставляем
      отдельными задачами: для них нужны новые поля листа и погодные правила.
- [ ] **Редактор (M).** Панель редактора получает быстрые кисти: `7` —
      дорога, `8` — трудная местность (болото, заросли, снег), `9` — сильное
      затемнение (дым/туман); ПКМ снимает выбранное свойство. `G` открывает
      инспектор клетки под курсором: укрытие и сторона, вода (нет/мелко/
      глубоко), течение и сила, профиль урона, свет, лазание, скользко; `Tab`
      и `↑`/`↓` — поле, `←`/`→` — значение, `Enter` — применить к клетке,
      `Esc` — закрыть. Урон задаётся выражением из `ParseDiceExpression`
      (как `/roll`), профили хранятся в палитре карты. Быстрые кисти и
      инспектор пишут в те же `CellProps` и работают с перетаскиванием из 2.5.
- [ ] **Отрисовка (M).** Слои поверх рельефа и под токенами: дорога, оттенок
      глубины воды, стрелки течения, штриховка трудной местности, дым/туман,
      метки укрытия на гранях, иконки урона, оттенок света. Подсказка панели
      объясняет значки; в игре клиенты видят те же свойства, что и хост.
      Сильное затемнение не должно скрывать сетку и границы карты — только
      содержимое за ним.
- [ ] **Сеть и сохранения (M).** `CellProps` и палитра урона входят в
      `GameSnapshot`/`GridMap`, поэтому едут в сейв, кампанию и `ViewUpdated`.
      Поднять `kSaveVersion`, `kProtocolVersion` и `kCampaignVersion`, обновить
      encode/decode со строгими проверками. Старые сцены: `kWater` — глубокая
      вода (плавание), `kTree` — трудная местность и слабое затемнение,
      `kLava` — профиль 10d10 огня; это меняет поведение воды в старых картах,
      отмечаем в заметках релиза.
- [ ] **Тесты (M).** `TestCellPropsRoundtrip` (все поля, границы, порча
      байтов), `TestMovementTerrainCost` (дорога, болото, вода, лазание,
      5–10–5), `TestCover` (стороны, половина/три четверти/полное, стены),
      `TestObscurement` (линия взгляда сквозь дым, слабое/сильное, скрытие
      токена), `TestHazardTriggers` (первый вход за ход, начало хода, спасбросок
      пополам, лава по умолчанию), `TestCurrent` (сдвиг, столкновение, провал
      Атлетики), `net_tests` — свойства доезжают до клиента, а укрытие и урон
      считает хост.
- [ ] **Документация и проверка (S).** `AGENTS.md` (свойства клеток, порядок
      расчёта движения, укрытие и урон), `README.md` (кисти и инспектор),
      `strings.h`, `PLAN.md` (версии форматов). Живое окно: нарисовать болото,
      дорогу, дым и лаву; проверить, что `M` сокращает путь по болоту и не
      сокращает по дороге; атака по цели за укрытием пишет +2/+5 и полное
      укрытие; вход в лаву снимает HP и пишет лог; дым скрывает токен снаружи;
      токен со скоростью плавания проходит глубокую воду; после `F5`, смены
      сцены и входа клиента всё совпадает. Скриншоты каждого изменённого вида.
- [ ] **Коммит** на русском: «Свойства клеток карты: местность, укрытия,
      вода, течение, дым и урон».

Порядок: модель и формат → движение, вода и дороги → укрытие → затемнение и
свет → урон и течение → редактор и отрисовка → сеть и тесты → живая проверка.
Это L: без миграции данных и без изменения правил движения не обойтись.

## Этап 3. Бой и правила (P1, M–L) — основа готова

Полный разбор расхождений с правилами — в аудите 22.11.2026: этап закрыт по
объёму, но не по всем правилам (смерть, отдых, концентрация, состояния,
действия в ход).

- [x] Автобросок инициативы в начале боя: сервер кидает d20 + бонус из листа
      за каждый токен, пишет результат в `initiative` и строку в лог. В листе
      появилось поле «Бонус инициативы».
- [x] Состояния с длительностью: `Condition{имя, секунды, КС}`; состояния из
      панели `K` ставятся на 1 минуту (`Shift+1–8` — до снятия), остаток виден
      в панели и на токене. В бою время идёт по 6 секунд за ход и тикает в
      начале хода своего токена; вне боя DM двигает время командой `/time N`
      (по умолчанию минуты, `s`/`m`/`h`), отдых тоже двигает время. В конце
      хода состояние с КС даёт спасбросок d20 + бонус спасброска; успех
      снимает состояние, итог пишется в лог.
- [x] Урон и лечение командой (`/damage N`, `/heal N` по выбранному токену):
      временные HP принимают удар первыми, при 0 HP ставится «без сознания»,
      лечение снимает его, всё пишется в лог.
- [x] Спасброски от смерти: `/deathsave` у токена с 0 HP, счётчики успехов и
      провалов в токене; 3 провала — «мёртв», 3 успеха — стабилен, 20 — 1 HP;
      удар по лежачему добавляет провал, лечение и отдых сбрасывают счётчики.
- [x] Отдых: короткий (`/rest`, 1 час и половина максимума HP) и длинный
      (`/longrest`, 8 часов, полный сброс HP, временных HP и состояний);
      объявляет только DM, итог пишется в лог. Время отдыха истекает у
      срочных состояний всех токенов.
- [x] Концентрация: при уроне сервер кидает d20 + бонус спасброска против
      10 или половины урона; провал снимает состояние, итог пишется в лог.
- [x] Применение шаблона области: `Enter` в режиме `F` готовит `/aoe 2d6 15`;
      сервер кидает урон один раз, каждому попавшему токену — спасбросок
      против сложности (успех уменьшает урон вдвое, провал — полный урон).

Порядок внутри этапа: урон → отдых → игровое время и длительность состояний →
автобросок → концентрация → область.

Приёмка: бой от начала до нуля HP у монстра целиком одним игроком и одним
DM-ом, лог читается как протокол боя.

## Этап 7. Раздача клиента и обновления (P1, M)

Решено: канал — публичный репозиторий на GitHub, релизы собираются локально,
автообновление полное (скачивание exe, проверка sha256, подмена, перезапуск).

Исходные условия: SDL3, SDL3_ttf и SDL3_image слинкованы статически
(`SDL_STATIC ON`), runtime MinGW — тоже, `WIN32_EXECUTABLE TRUE` — на выходе
один `virtual_dnd_tabletop.exe` без DLL и без консоли, установщик не нужен. Данные
стола лежат рядом с `.exe` (`SDL_GetBasePath()`): `savegame.bin`, `*.dndcamp`,
`session.log`, подложки, портреты, `assets/fonts/DejaVuSans.ttf`. Значит
обновление — подмена только `.exe`, папку игры трогать нельзя. Протокол
строгий (`kProtocolVersion`), а сохранения и кампании читаются начиная с
v0.1.0: `kMinSaveVersion = 26`, `kMinCampaignVersion = 13`, и декодер по
версии файла знает, каких полей в нём нет. Версия теперь приходит из
`git describe` на configure: на теге — `v0.2.0`, без тега — `0.0.0-dirty`
(developer build).

### 7.4 Скачивание и подмена exe

Windows разрешает переименовать запущенный `.exe`, но не удалить — на этом и
строится обновление без установщика и без прав администратора.

- [x] Скачивание в `virtual_dnd_tabletop.update.exe` рядом с текущим exe;
      проверка размера и `sha256` из манифеста (переиспользуется
      `src/core/sha256`, файл читается в память целиком — около 20 МБ).
- [x] Проверка, что папка доступна на запись; если нет (игра в
      `Program Files`) — самообновление отключается, остаётся кнопка
      «Скачать в браузере» (`SDL_OpenURL`).
- [x] У хоста перед подменой — `CampaignSaver::Flush()`, чтобы не потерять
      окно автосейва.
- [x] Подмена: `virtual_dnd_tabletop.exe →
      virtual_dnd_tabletop.old.exe`, `virtual_dnd_tabletop.update.exe →
      virtual_dnd_tabletop.exe`, `CreateProcess` нового бинарника, старый
      процесс выходит; `virtual_dnd_tabletop.old.exe` удаляется на старте.
- [x] Откат: если второй rename не удался (антивирус держит файл) —
      `virtual_dnd_tabletop.old.exe → virtual_dnd_tabletop.exe` и понятный
      текст ошибки.
- [x] `PlanStartupRecovery` в `src/core/update`: комбинации
      `virtual_dnd_tabletop.exe` / `virtual_dnd_tabletop.old.exe` /
      `virtual_dnd_tabletop.update.exe` → `None`, `RestoreOld`, `FinishSwap`,
      `Cleanup`; вызывается до создания окна, тест `TestStartupRecovery` на
      все комбинации — обрыв между шагами не должен оставлять «игра не
      запускается».
- [x] Именованный мьютекс на путь папки (`src/app/instance_lock`): два
      экземпляра из одной папки не запускаются, иначе
      `virtual_dnd_tabletop.old.exe` залочен и подмена ломается. Перед

- [x] Подмена только в меню: во время сессии — баннер «Обновление после
      выхода из меню», стол не теряется.

### 7.5 Несовпадение версий

`Reject` уже несёт обе версии; добавляется третья — последняя в манифесте, и
вердикт из `UpdateAdvice` (`src/core/update`, тест `TestUpdateAdvice`):

| моя | хоста | последняя | вердикт |
| --- | --- | --- | --- |
| 35 | 36 | 36 | «Обновитесь» + кнопка обновления |
| 36 | 35 | 36 | «Хост на старой версии, пусть DM обновится» |
| 36 | 36 | 37 | «Совместимы, есть более новая» — игру не блокирует |
| ? | 36 | нет сети | «Версии не совпадают, проверьте вручную» + ссылка на релизы |

- [x] Диалог mismatch: версии обеих сторон, последняя из манифеста, кнопка
      обновления, если она помогает. Подробности уходят отдельным кадром
      `VersionMismatch` сразу после текстового `Reject`: протокол и версия
      хоста плюс версия из его манифеста. Старые сборки неизвестный тип
      пропускают и видят прежний текст, поэтому бамп протокола не нужен.
      Диалог модальный: `Esc` или «Закрыть» возвращают меню, `Enter` —
      обновление; у developer build вместо кнопки обновления «Страница
      релизов».
- [x] Обратную совместимость протокола на две версии не делаем: это
      версионирование каждого сообщения, дорого при 8 игроках; разнообразие
      версий лечим одним нажатием.
- [x] Хост обновляется первым: баннер у него появляется раньше, чем клиенты
      начнут получать отказ (проверка обновлений идёт при старте, во время
      партии DM видит «Доступна версия X — обновление после выхода в меню»).

## Этап 8. Кампания и оверлей партии (P1, M–L) — план

Сейчас игра пишет в саму кампанию: автосейв, `F5`, смена сцены, `N`/`Del`/`R`
заменяют снимки и структуру `*.dndcamp`. После одной партии файл кампании
становится слепком именно её, и провести по нему вторую игру уже нельзя.
Делим хранение на два слоя:

- **Кампания** (`*.dndcamp`) — авторский шаблон. В игре открывается только на
  чтение, меняется только редактором.
- **Оверлей партии** (`<имя кампании>.dndoverlay`) — всё, что наработал стол:
  снимки сыгранных сцен (туман, HP, состояния, позиции, время, бой), новые,
  удалённые и переименованные сцены, активная сцена. Пишет только хост, рядом
  с кампанией.

Оверлей сцены — полный `GameSnapshot`, а не дельта по полям: за партию меняется
почти всё, а дельта потребовала бы второго сериализатора и правил слияния.
Снимок хранится только для сцен, где играли; остальные берутся из кампании.
Отсюда и повторное использование: новый оверлей — новая партия, файл кампании
не тронут.

Что в исходной идее нужно уточнить:

1. **Оверлею нужна стабильная идентичность сцен.** Имя меняется, индекс
   съезжает при удалении. В `Scene` появляется `id` (`std::uint64_t`), в
   `Campaign` — монотонный `next_scene_id`, который не переиспользует номера.
   Сцены, созданные в игре, получают id из отдельного диапазона
   (`kOverlaySceneIdBase = 1ull << 63`), чтобы поздняя правка кампании не
   столкнулась с ними. Старые кампании при чтении получают id 1..N по порядку
   и сохраняют их при следующей записи.
2. **Структурные операции в игре — тоже оверлей.** `N`, `Del`, `R`, `E` и
   активная сцена сейчас меняют `campaign_`; теперь они пишут в оверлей:
   добавленная сцена, tombstone на удалённую, переопределение имени и заметки.
   Активная сцена хранится по id, а не по индексу.
3. **Редактор не должен видеть оверлей.** `StartEditor` обязан перечитывать
   кампанию с диска без партии, иначе правка в редакторе снова затащит
   состояние игры в шаблон. `F5` в редакторе пишет кампанию и
   `scene.dndscene`, `F5` в игре — оверлей.
4. **Оверлей — это продолжение партии, а не тихий автосейв.** В меню хоста
   видно «Партия: продолжение, сцен N» или «Партия: новая». Новая партия —
   отдельное действие с подтверждением, иначе вторая игра молча продолжит
   первую. Без файла кампании оверлей не грузится: сначала восстанавливают
   шаблон, оверлей не удаляется.
5. **Кампания может измениться между сессиями.** В оверлее хранится отпечаток
   (FNV-1a) прочитанной кампании. При расхождении оверлей не применяется, пока
   DM не подтвердит: иначе подменённая кампания с теми же id смешается с
   партией. После подтверждения отпечаток обновляется; сыгранные сцены
   остаются из оверлея, несыгранные подтягиваются из новой кампании.
   Отдельное действие «сбросить сцену к кампании» убирает запись оверлея для
   одной сцены.
6. **Обратный путь нужен явно.** Иначе карта, переделанная в игре, навсегда
   останется только в партии. Позже (P2) — команда DM «внести сцену/партию в
   кампанию» с подтверждением; в MVP её нет, и это сказано в `README.md`.
7. **Третий источник правды убираем.** `savegame.bin` дублирует оверлей.
   Предлагается: `F5` в игре — явное сохранение оверлея (`Flush`), `F9` —
   перечитать оверлей с диска; `savegame.bin` больше не пишется. `F5`/`F9`
   редактора (`scene.dndscene`) остаются шаблоном/импортом одной сцены.
8. **Автосейв и выход.** `CampaignSaver` получает вторую работу — оверлей; в
   кадре по-прежнему только копия. При закрытии окна `CampaignSaver` сейчас
   выбрасывает недописанную работу — перед `Shutdown` нужен `Flush` оверлея,
   иначе последние 8 секунд партии теряются.
9. **Запись оверлея атомарная** (временный файл + `rename`): обрыв на записи не
   должен стоить партии. Повреждённый оверлей не затирается и не игнорируется
   молча: отказ с текстом, файл остаётся для разбора.

Схема файла:

```
DNDO, версия, размер
  отпечаток кампании, активный scene id, следующий scene id
  записи: id, флаги (удалена / имя / заметка / снимок), name, note, snapshot
```
